# FinPassport

**An AI agent that helps international students send more money home.**

Team FinPassport · 2026 Shenzhen International FinTech Competition (FinTechathon) · International Track · Topic C: Cross-border & Student Finance Assistant

Team: Kaniz Fatima Daya (leader), Muhammed Nazmul Arefin, Raisa Rahman Prionty

> Sandbox prototype. All rates, providers (GulfXpress, QuickRemit, DeshLink, Bank wire) and accounts are simulated. No real money moves.

## What it does

FinPassport is a chat agent for the Saudi Riyal (SAR) to Bangladeshi Taka (BDT) corridor. It:

- tells you if today is a good day to send, with an **AI forecast** of the next 7 days (a range, not a single number);
- sets rate alerts and tells you when the rate reaches your target (alerts never move money);
- ranks four providers by what an **AI provider learner** expects to actually arrive (fee + rate markup + hidden losses learned from receipts);
- checks every transfer with a **federated fraud model** trained across providers without sharing customer data;
- sends money only after the right level of approval;
- schedules tuition payments with a reminder 3 days before the due date;
- holds SAR, USD and BDT balances and converts SAR <-> USD;
- explains every step and records it in an audit log.

## Run it

No installation is needed for the app.

1. Download or clone this repository.
2. Open `src/index.html` in Chrome, Edge, Firefox or Safari.

Run the tests (Node.js 18 or newer):

```bash
npm test
# or
node --test tests/agent.test.js
```

Expected result: `# pass 26` and `# fail 0`.

Retrain the AI models (Python 3 with numpy, pandas, scikit-learn):

```bash
cd ml
pip install -r requirements.txt
python forecast.py          # model 1: rate forecast + backtest
python fraud_seeds.py       # model 2: federated fraud detection, 5 seeds
python provider_bandit.py   # model 3: provider learner (Thompson sampling)
python build_models.py      # bundles all three into src/models.js
```

## How it works

Every request goes through six stages:

1. **Understand** – intent and details (amount, currency, recipient, date)
2. **Plan** – ordered tool calls, shown to the user
3. **Guard** – the policy engine runs 7 risk checks and assigns a permission tier
4. **Ask** – one tap (Tier 1) or approval + one-time code (Tier 2); Tier 3 is refused
5. **Act** – the policy is checked again, then the sandbox ledger is updated
6. **Explain and log** – reasons in the chat, every step in the audit log

The AI proposes, the policy engine decides. In this prototype, step 1 is a rule-based parser so the demo is reproducible without an API key. In production, a language model with function calling replaces only step 1; tools, policy engine and log stay the same.

### The three AI models (all trained on simulated data)

| Model | Method | Held-out result |
| --- | --- | --- |
| Rate forecast | 21 linear quantile regressions (7 horizons × 10/50/90% quantiles) + a send-now-or-wait rule | +22 BDT per 1,000 SAR vs. always sending today (18% of perfect hindsight); 7-day error 7% lower than a naive baseline |
| Federated fraud detection | 10-16-1 neural network trained with FedAvg across 3 providers (optional clipping + Gaussian noise) | 54% of fraud caught at 1% false alarms vs. 27–36% for any provider alone and 56% with all data pooled |
| Provider learner | Contextual Thompson sampling with Bayesian linear regression on hidden losses | 0.2 BDT lost per 1,000 SAR vs. the true best provider, compared with 29.7 for always picking the best quote |

The fraud score is the eighth policy check: 0.5+ needs Tier 2, 0.9+ is blocked, with the three main reasons shown.

### Tools

`get_rate`, `rate_insight`, `forecast_rate`, `compare_providers`, `fraud_score`, `send_transfer`, `learn_from_receipt`, `set_rate_alert`, `schedule_payment`, `convert_currency`, `get_balances`

### Permission tiers

| Tier | When | User action |
| --- | --- | --- |
| 0 · Auto | No money moves (rate, compare, balances, alerts) | None, logged |
| 1 · Confirm | Known recipient, up to 1,000 SAR, normal pattern; own-account conversion | One tap |
| 2 · Approve + code | New recipient, over 1,000 SAR, over 3x usual amount, 3+ transfers today, scheduled payments, AI fraud score 0.5+ | Approval + 6-digit code (3 attempts) |
| 3 · Blocked | Sanctions watchlist match, over 5,000 SAR/day, not enough balance, AI fraud score 0.9+, prompt injection, request to change limits | Cannot be approved |

### Other safeguards

- Code bound to one request; 3 wrong codes cancel it
- Policy re-checked right before money moves
- Pending approvals expire when the rate changes (new day)
- Prompt-injection guard; the agent has no tool to change limits or trust
- Append-only audit log (Activity log tab → Copy log as JSON)

## Demo script

Use the suggestion buttons above the message box:

1. **Good day to send?** → 7-day forecast chart: likely better in 5 days, 30% chance it ends lower → tap **Alert me when…**
2. Press **Next day →** three times → the alert fires on Fri 23 Oct
3. **Send 1000 SAR to Ammu** → Tier 1 → **Confirm** → receipt
4. **Scam: agent deposit** → the federated fraud model scores 0.91 and blocks it, with reasons
5. Wallet tab → tick **Simulate a stolen login** → **Send 3000 SAR to Ammu** → fraud score 0.84, Tier 2; the AI picks QuickRemit over the best quote → enter the code from the simulated SMS → **Approve**
6. **Try an unsafe request** → Tier 3, refused
7. **AI models** tab → results of all three models; **Activity log** tab → every step recorded

**Reset demo** starts over.

## Limitations

Simulated data only (rates, fraud labels and provider receipts are not public); the one-time code is shown on the same screen; no login; data is kept in browser memory. See the technical documentation for the full known-risk list and roadmap.
